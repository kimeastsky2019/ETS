# 진단문서 위키 표준화 — 스킬 기획 및 착수 가이드

> **목표**: 에너지진단 보고서가 "읽는 문서"에서 **"다시 쓰이는 데이터"** 가 된다.

| 항목 | 내용 |
| --- | --- |
| 문서 버전 | v1.0 (2026-08-22) |
| 대상 | 진단원 10명 · 도메인 리드 · 계수 관리자 · 운영 관리자 |
| 산출물 | `.claude/skills/ets-wiki-ingest`, `.claude/skills/ets-wiki-review` |
| 연동 | ETS 통합 플랫폼 `/work/wiki`, `/work/diagnosis`, `/work/benchmark` |

## 0. 완료 정의

"표준화했다"는 말이 측정 가능해야 한다. 아래 셋을 완료 기준으로 둔다.

1. **신규 진단 착수 시**, 사업장 조건을 넣으면 유사 사례 3건과 ECM 후보 5건이 10분 안에 나온다.
2. **같은 개선안이 같은 슬러그로** 불린다. 사업장이 달라도 카드 하나가 계속 자란다.
3. **수치의 출처를 항상 되짚을 수 있다.** 어떤 값이든 원문 페이지까지 3클릭 안에 도달한다.

## 1. 스킬 아키텍처 — 왜 업종별 스킬이 아닌가

업종마다 스킬을 만드는 방식을 먼저 검토했고, 채택하지 않았다.

| | 업종별 스킬 12개 | **공통 스킬 2개 + 업종 프로파일 12개** |
| --- | --- | --- |
| 공통 규칙 변경 | 12곳 수정 | 1곳 수정 |
| 규칙 일관성 | 시간이 지나며 갈라짐 | 구조적으로 하나 |
| 새 업종 추가 | 스킬 신규 작성 (수백 줄) | 프로파일 파일 1개 (~60줄) |
| 업종 지식 작성자 | 스킬 작성 가능한 사람 | **진단원 누구나** |
| 유지 주체 | 개발 | 진단팀 |

업종마다 다른 것은 **규칙이 아니라 데이터**다. 데이터 컨트랙트·명명·단위·ACL 판정은 12업종이 같고,
"이 업종 보고서에서 함수율은 어느 표에 있는가"만 다르다. 그래서 규칙은 스킬에, 지식은 프로파일에 둔다.

### 구성

```
.claude/skills/
├── ets-wiki-ingest/              # 원문 → 위키 문서 (생성)
│   ├── SKILL.md                  # 절대 규칙 5개, 입력 검사, 8단계 절차
│   ├── references/
│   │   ├── contract.md           # front-matter 필드 정의와 판정 규칙
│   │   ├── naming.md             # 슬러그 명명 규칙, 표기 변형 통일
│   │   ├── units.md              # 단위 표기와 함정
│   │   └── sectors/              # ★ 업종 지식 — 진단팀이 채운다
│   │       ├── README.md         # 작성 상태표 + 작성 방법
│   │       ├── _TEMPLATE.md      # 5개 절 고정 서식
│   │       ├── waste.md          # 초안
│   │       ├── building.md       # 초안
│   │       └── machinery.md      # 초안
│   └── templates/                # 문서 타입별 본문 서식 7종
└── ets-wiki-review/              # draft → reviewed (검수)
    ├── SKILL.md                  # 검수 순서, 승격 기준, 우선순위
    └── references/lint-rules.md  # Lint 9종 판정 기준
```

### 서비스와의 부합

스킬 산출물은 플랫폼 스키마와 1:1 대응한다. 별도 변환 계층이 없다.

| 스킬이 만드는 것 | 플랫폼에서 받는 곳 |
| --- | --- |
| front-matter 11필드 | `wiki_pages` 컬럼 |
| 문서 타입 9종 | `wiki_pages.type` 닫힌 집합 |
| 업종 코드 | `energy-taxonomy.ts` 12종 |
| 정량 데이터 (분리 인계) | `diagnoses` · `diagnosis_measures` |
| 계수 확인 요청 | `energy_factors` SSOT |

**스킬이 절대 하지 않는 일**: 숫자 계산. 환산·합산·회수기간은 전부 플랫폼 계산 엔진이 한다.
스킬은 원문에서 값을 정확히 옮기는 데까지만 책임진다.

## 2. 표준화의 실체 — 네 개의 축

"표준화"를 막연히 두면 아무것도 안 된다. 고정할 대상은 넷뿐이다.

| 축 | 고정하는 것 | 깨지면 생기는 일 |
| --- | --- | --- |
| **식별** | 슬러그 명명 규칙 (`ecm-`, `eqp-`, `dgn-` …) | 같은 개선안이 두 이름으로 갈려 과거 실적이 분산된다 |
| **컨트랙트** | front-matter 11필드 + 판정 규칙 | 검색·ACL·검산 게이트가 전부 무력화된다 |
| **본문** | 타입별 템플릿 (섹션 고정) | 사람마다 다른 순서로 써서 비교가 안 된다 |
| **관계** | `[[슬러그]]` 링크와 ACL 상속 | 지식이 섬으로 흩어지고, 기밀이 낮은 등급으로 샌다 |

가장 자주 깨지는 축은 **식별**이다. `ecm-waste-heat-recovery-boiler` 와 `ecm-economizer-boiler`가
따로 살면 회수기간 실적이 두 곳으로 갈라져 ECM 추천이 망가진다.
그래서 스킬은 문서를 만들기 전에 **기존 슬러그 검색을 강제**한다.

## 3. 작업자가 해야 할 일

### 3.1 역할

| 역할 | 인원 | 책임 |
| --- | --- | --- |
| **진단원** (문서 오너) | 진단 수행자 전원 | 자기 진단 건의 위키화 · 정량 등록 · 수치 검산 |
| **도메인 리드** | 업종군당 1명 | 업종 프로파일 작성 · ECM 카드 신설 승인 · 중복 병합 판정 |
| **계수 관리자** | 1명 | 고시 원문 확인 · 계수 표 확인 처리 · 개정 추적 |
| **운영 관리자** (admin) | 1명 | 계정·ACL 정책 · 주간 Lint 배치 확인 · 반출 승인 대장 |

10명 조직이므로 겸임이 정상이다. 다만 **계수 관리자는 반드시 한 사람으로 고정한다.**
계수가 여러 사람 손을 타면 어떤 값으로 계산됐는지 추적이 끊긴다.

### 3.2 문서 1건 처리 파이프라인

| # | 단계 | 담당 | 자동 | 소요 |
| --- | --- | --- | --- | --- |
| 1 | 반출·활용 동의 확인, 대장 기록 | 진단원 | 수동 | 5분 |
| 2 | 파일 정리·명명, 부속 자료 첨부 | 진단원 | 수동 | 10분 |
| 3 | 입력 조건 검사 (반려 판정) | 스킬 | **자동** | – |
| 4 | 업종 판정 | 스킬 제안 → 진단원 확정 | 반자동 | 3분 |
| 5 | 문서 분해·생성 (source/facility/equipment/measure/diagnosis) | 스킬 | **자동** | – |
| 6 | 진단 원장에 정량 등록 (`/work/diagnosis`) | 진단원 | 수동 | 10분 |
| 7 | **수치 검산** — 원문 대조 후 `numericVerified` | 진단원 | 수동 | 15~25분 |
| 8 | 검수 및 `reviewed` 승격 | 도메인 리드 | 수동 | 10분 |

**100면 보고서 1건당 사람 손이 가는 시간은 약 50~60분**이다.
초기 10건은 규칙에 익숙해지는 중이라 90분까지 잡는다.

수동 단계 중 **7번이 전부다.** 나머지는 절차이고, 7번이 이 시스템의 신뢰를 만든다.
검산하지 않은 수치는 AI 응답에도, 벤치마크에도, 보고서 초안에도 들어가지 않는다.

### 3.3 주간 루틴

| 주기 | 담당 | 할 일 |
| --- | --- | --- |
| 매주 월 | 운영 관리자 | Lint **차단 항목** 확인 → 담당자 배정 |
| 매주 수 | 도메인 리드 | 신규 ECM 카드 후보 리뷰 · 중복 병합 판정 |
| 매주 금 | 계수 관리자 | 계수·단가 개정 확인, 유효기간 임박 건 갱신 |
| 매월 말 | 운영 관리자 | 벤치마크 표본 갱신 (사업장당 최신 1건 유지) |

Lint를 미루면 후단에서 폭발한다. 위키가 깨진 상태로 검색 인덱스를 만들면
문제 발견 시 **소스부터 인덱스까지 전부 재생성**해야 한다. 주 1회 30분이 나중에 며칠을 아낀다.

### 3.4 도메인 리드의 첫 임무 — 업종 프로파일

지금 9개 업종 프로파일이 비어 있다. **이것이 착수 첫 주의 최우선 작업이다.**

`_TEMPLATE.md`의 5개 절을 채운다. 절당 3~5줄이면 충분하다.

1. 업종 판정 포인트 — 어휘, 설비, 헷갈리는 업종과의 구분
2. 필수지표 확인처 — 보고서 어느 표·어느 절에 있는가
3. 표 읽기 주의 — 이 업종에서 오독하기 쉬운 지점
4. 자주 나오는 ECM — 카드 슬러그 또는 후보
5. 단위·용어 함정

작성 기준: **그 업종 보고서를 처음 보는 진단원이 이 파일만 읽고 위키화할 수 있는가.**
1개 작성에 60~90분. 9개 = 약 12시간, 담당을 나누면 1주 안에 끝난다.

> 없는 지식을 스킬이 지어내면 위키 전체의 신뢰가 무너진다.
> 업종 판정 기준은 **그 업종 진단 경험이 있는 사람만** 쓸 수 있다.

## 4. 원본 데이터의 조건

### 4.1 필수 조건 (하나라도 없으면 반려)

| # | 조건 | 확인 방법 |
| --- | --- | --- |
| 1 | 고객사 반출·활용 동의 | 계약 조항 또는 별도 동의서. 대장에 기록 |
| 2 | 텍스트 레이어가 있는 PDF | 본문 한 문단을 복사해 붙여넣어 본다 |
| 3 | 표 구조 보존 | 사용량 표 하나를 복사해 **행·열이 유지되는지** 본다 |
| 4 | 필수 3개 절 | 사업장 개요 / 에너지사용현황 / 개선안(절감효과 포함) |
| 5 | 진단 연도 특정 가능 | 표지 또는 개요 |
| 6 | 업종 판정 가능 | 공정 설명 또는 업종 명시 |
| 7 | 원단위 분모 값 | 연면적 / 생산량 / 처리량 중 해당 업종의 분모 |

**3번이 가장 자주 걸린다.** 에너지진단 보고서는 수치가 전부 표에 있어서,
표 구조가 깨진 상태로 위키화하면 문서의 절반이 근거 없이 만들어진다.
스캔본이거나 표가 이미지인 경우 **OCR·표 추출을 먼저 처리한 뒤** 파이프라인에 넣는다.

### 4.2 있으면 품질이 크게 오르는 부속 자료

| 자료 | 왜 필요한가 | 우선순위 |
| --- | --- | --- |
| 12개월 에너지 구매·청구 내역 (XLSX) | 보고서 표의 수치를 교차 검증한다 | 높음 |
| 설비 리스트 (용량·대수·가동시간) | 설비 문서와 ECM 적용 조건 판정 | 높음 |
| **개선 후 실적 (사후 검증 자료)** | **회수기간 실적의 유일한 근거** | 높음 |
| 15분·시간 단위 계측 데이터 | 부하 프로파일 → 인버터류 ECM 판정 | 중간 |
| 운전일지 | 실가동 시간 확인 | 중간 |
| 공정 흐름도 · 물질수지도 | 폐기물·화학 업종에서는 사실상 필수 | 업종별 |

사후 검증 자료가 없으면 ECM 카드에 **제안 회수기간만 남고 실제 회수기간이 없다.**
"과거 실제 회수기간 분포"가 이 위키의 핵심 가치인데, 그게 비게 된다.
**과거 진단 중 사후 실적이 있는 건을 우선 선별하라.**

### 4.3 연도와 중복 처리

- **최근 5년 이내**를 우선한다. 그보다 오래된 건은 단가·계수 개정 때문에 벤치마크를 오염시킨다.
- 5년 초과분은 **ECM 패턴 추출용으로만** 쓰고 `measurementBasis`를 낮춰 잡는다.
- 같은 사업장 재진단은 `dgn-2024-hanbit`, `dgn-2027-hanbit`처럼 연도로 구분해 시계열로 연결한다.
- **벤치마크 표본은 사업장당 최신 1건만** 넣는다. 같은 사업장이 여러 번 들어가면 분포가 그 사업장 쪽으로 끌린다.

### 4.4 보안 사전 분류

파일을 넘기기 전에 진단원이 등급을 정한다. 스킬이 추정하지 않는다.

| 등급 | 이 보고서가 | 외부 모델 |
| --- | --- | --- |
| `internal` | 고객사 식별 정보를 지운 표준화 자료 | 가능 |
| `confidential` | 사업장명·설비 사양·사용량 실적 포함 (**대부분의 진단 보고서**) | 차단 |
| `restricted` | 계약상 취급 제한 명시, 도면, 개인정보 포함 | 차단 |

애매하면 높은 쪽으로 올린다. 낮춰서 생기는 사고가 높여서 생기는 불편보다 크다.

## 5. 원본 데이터의 수량

### 5.1 왜 수량이 문제인가

원단위 벤치마크에서 사분위수가 의미를 가지려면 표본이 일정 수 이상이어야 한다.

- 표본 10건: 1건이 들고 나면 p25·p75의 순위가 통째로 밀린다. 분포라고 부르기 어렵다.
- 표본 20건: 사분위수가 안정되기 시작한다. **실무 최소선.**
- 표본 30건 이상: 중앙값이 표본 1~2건 변동에 흔들리지 않는다.

ECM 카드는 다른 기준이다. **같은 패턴이 3건 이상 관측되어야 "패턴"이라 부를 수 있다.**
1~2건짜리 관찰은 해당 진단 문서에 남기고 카드로 올리지 않는다.

### 5.2 단계별 수량 계획

| 단계 | 기간 | 보고서 수량 | 구성 | 목적 |
| --- | --- | --- | --- | --- |
| **Phase 0 — 파일럿** | 2주 | **30건** | 대표 3업종 × 10건 | 스킬 튜닝, 게이트 검증, 공수 실측 |
| **Phase 1 — 코어 구축** | 8주 | **200~240건** | 주력 6업종 × 30~40건 | 벤치마크 성립, ECM 카드 30~40장 |
| **Phase 2 — 확장** | 12주 | **+260건** | 나머지 업종 + 최신 재진단 | 12업종 전부 표본 20건 이상 |

Phase 1의 200건은 이렇게 나온다: 주력 6업종 × 30건 = 180건, 여기에 보정 여유 20건.
**업종당 30건은 사업장 30곳**을 뜻한다 (재진단은 최신 1건만 표본).

### 5.3 업종별 최소선

| 표본 수 | 쓸 수 있는 것 | 쓸 수 없는 것 |
| --- | --- | --- |
| 1~9건 | 유사 사례 검색, ECM 후보 | 벤치마크 분포 |
| 10~19건 | + 중앙값 참고 | 사분위수 판정 |
| **20건 이상** | + 사분위수, 백분위 위치 | – |
| 30건 이상 | + 안정적 벤치마크 | – |

표본 20건 미만인 업종은 **벤치마크 화면에서 분포를 보여주되 "참고" 표시**를 붙인다.
없는 통계를 있는 것처럼 보여주면 진단원이 한 번 데이고 다시는 안 쓴다.

### 5.4 ECM 카드 수량

보고서 1건에는 개선안이 보통 5~8건 들어 있다. Phase 0의 30건이면 **개선안 관측 150~240건**.
패턴 3건 기준으로 묶으면 **초기 카드 20~30장**이 나온다. 이 정도면 ECM 추천이 실용적으로 작동한다.

카드가 100장을 넘어가면 오히려 중복이 문제가 된다. 도메인 리드의 주간 병합 판정이 그래서 필요하다.

### 5.5 배치와 검수 규모

| 항목 | 규모 | 근거 |
| --- | --- | --- |
| 1회 ingest 배치 | **10~15건** | 한 번에 몰아넣으면 디테일 준수가 무너진다 |
| 수치 검산 | **전수** (measure · metric · diagnosis) | 수치가 있는 문서는 예외 없이 |
| 문서 검수 | 전수 (규정·ECM), 담당 진단원 (사업장·진단), **10% 샘플** (원문 요약·인사이트) | 사용 빈도 순 |
| Phase 0 검수 공수 | 30건 × 60~90분 ≈ **30~45시간** | 진단원 2명 × 2주 중 부분 투입 |

## 6. 품질 게이트

각 단계는 게이트를 통과해야 다음으로 간다. **통과 못 하면 수량을 늘리지 않는다.**

### Phase 0 게이트

- [ ] 표 데이터 정확도 ≥ 95% (검수 시 원문 대조)
- [ ] front-matter 스키마 준수율 ≥ 98%
- [ ] 업종 판정 정확도 ≥ 90% (진단원 확정과 스킬 제안의 일치율)
- [ ] Lint **차단** 0건
- [ ] 1건당 사람 공수 ≤ 90분

### Phase 1 게이트

- [ ] Lint 차단 0건 (주간 배치 기준)
- [ ] 수치 검산 통과율 ≥ 95%
- [ ] 주력 6업종 전부 표본 20건 이상
- [ ] ECM 카드 20장 이상, 각 카드에 적용 사례 3건 이상
- [ ] 유사 사례 검색 만족도 — 진단원 대상 "쓸 만하다" ≥ 70%

### 상시 KPI

| 지표 | 목표 |
| --- | --- |
| Lint 차단 건수 | 0 |
| 미확인 환산계수 | 0 |
| ECM 카드 재사용률 | 신규 진단당 3건 이상 |
| 자료 탐색 시간 (설문) | −40% |
| 보고서 작성 시간 | −20% |
| ACL 위반 사고 | 0 |

## 7. 4주 착수 계획

| 주 | 담당 | 할 일 | 산출 |
| --- | --- | --- | --- |
| **D+3** | 진단팀 | 파일럿 30건 선별 (사후 실적 있는 건 우선) + 반출 승인 | 파일럿 목록 |
| **W1** | 도메인 리드 | 업종 프로파일 9개 작성 | `sectors/*.md` |
| **W1** | 계수 관리자 | 환산계수 8종 고시 확인 → 확인 처리 | 계수 표 차단 0건 |
| **W2** | 진단원 2명 | 파일럿 10건 위키화 + 전수 검수 | 품질 기준선, 공수 실측 |
| **W2** | 개발 | 검수 결과로 스킬 규칙 보정 | 스킬 v1.1 |
| **W3** | 진단원 | 파일럿 20건 추가 | 문서 60~80건 |
| **W3** | 도메인 리드 | 중복 병합 · ECM 카드 신설 | 카드 20장 |
| **W4** | 전원 | Phase 0 게이트 리뷰 | 통과 여부 판정 |

**W1의 업종 프로파일 작성이 임계 경로다.** 프로파일 없이 위키화하면 업종 판정이 틀리고,
업종이 틀리면 필수지표와 원단위 분모가 전부 틀어져 다시 해야 한다.

## 부록. 스킬 사용법

```
# 위키화
/ets-wiki-ingest   (또는 "이 진단 보고서를 위키로 만들어줘")

# 검수
/ets-wiki-review   (또는 "Lint 차단 항목 정리해줘")
```

스킬은 `.claude/skills/` 에 있으므로 이 저장소에서 Claude Code를 열면 바로 인식된다.
업종 프로파일을 추가하면 다음 실행부터 반영된다 — 스킬을 다시 만들 필요가 없다.
